An integration connects an account from another service to a library. WingDrive maps what the account offers onto its own concepts: storage becomes a cloud volume that the Explorer, copy jobs and cloud sync already understand, and services without a file tree get their own jobs. Providers are Google (Google Drive and Google Photos) and Microsoft (OneDrive).

## Connection modes

Every sign-in goes through an OAuth client registered with the provider. Settings > Integrations shows one card per service and mode, and the user picks whose client signs them in:

| Mode | Google card | Microsoft card | What the user does |
| --- | --- | --- | --- |
| `app` | Google account | Microsoft account | Only signs in. WingDrive's own client, included in official builds, does the rest. |
| `custom` | Google Cloud | Microsoft Entra | Registers their own client first, saves it in the library, then signs in. |

The `app` mode is the quick path. It depends on the client in the build (INTG-001 for Google, INTG-022 for Microsoft), and until the provider verifies WingDrive's app, the consent page warns that the app is unverified and caps how many people can sign in. API quotas are shared by everyone using WingDrive's client.

The `custom` mode works in any build, including builds from source, and keeps the project, quotas and access control with the user. It takes a few minutes in Google Cloud Console or Microsoft Entra. A Google consent screen left in testing mode ends grants every 7 days.

Each account stores the client it signed in with and its mode (`IntegrationAccountInfo.mode`), because a refresh token only works with the client that issued it. Google accounts saved before modes existed count as `custom` when their client matches the one saved in the library, and `app` otherwise. Starting a sign-in in a mode without a client fails with `AppClientMissing` or `CustomClientMissing`.

## Signing in

WingDrive uses the OAuth flow Google recommends for desktop apps:

1. The daemon opens a one-shot HTTP listener on a random `127.0.0.1` port.
2. The browser shows Google's consent page for the services you selected.
3. Google redirects to the listener with an authorization code.
4. The daemon trades the code for tokens and reads the account profile.

PKCE (RFC 7636) binds the code to the daemon, so another local process that sees the redirect cannot redeem it. The `state` parameter must match, and a redirect with a different `state` is ignored instead of cancelling the sign-in. The session expires after 10 minutes.

Connecting the same account again merges the grants, which is how you add Photos to an account that only granted Drive. Accounts are keyed by Google's stable account ID, not by email.

### OAuth client

WingDrive's own Google client (mode `app`) comes from `WINGDRIVE_GOOGLE_CLIENT_ID` and `WINGDRIVE_GOOGLE_CLIENT_SECRET` in the daemon's environment, or the same variables at build time, compiled into the binary. The user's own client (mode `custom`) is saved in the library from the Google Cloud card in Settings > Integrations, or with `wing integrations google-client set`.

To create your own client:

1. In [Google Cloud Console](https://console.cloud.google.com/), create a project.
2. Enable the Google Drive API, the Photos Library API and the Photos Picker API.
3. Configure the OAuth consent screen. While the app is in testing mode, add your accounts as test users. Testing-mode grants expire after 7 days; publish the app to keep them.
4. Create credentials of type **OAuth client ID** with application type **Desktop app**.
5. Paste the client ID and secret in the Google Cloud card of Settings > Integrations, or run:

```bash
wing integrations google-client set --client-id 1234-abc.apps.googleusercontent.com --client-secret GOCSPX-...
wing integrations connect google --own-client
```

A desktop client secret is not confidential, but Google still requires it in the token request. Accounts keep the client they signed in with, because a refresh token only works with the client that issued it.

## OneDrive

Microsoft accounts (personal, work or school) sign in against the Microsoft identity platform's `common` endpoint as a public client: PKCE and no client secret. The redirect goes to `http://localhost:<port>/oauth/callback`, served by the same loopback listener as Google, because Microsoft only lets app registrations list `localhost` with any port.

Scopes are `openid profile email offline_access User.Read Files.ReadWrite`. `Files.ReadWrite` covers the user's own OneDrive and, unlike `Files.ReadWrite.All`, needs no admin consent in most tenants.

WingDrive's own app registration (mode `app`) comes from `WINGDRIVE_MICROSOFT_CLIENT_ID` in the daemon's environment or at build time. To use your own (mode `custom`):

1. In [Microsoft Entra](https://entra.microsoft.com/), open **App registrations > New registration**.
2. Under **Supported account types**, choose accounts in any organizational directory and personal Microsoft accounts.
3. Under **Redirect URI**, choose **Public client/native (mobile & desktop)** and enter `http://localhost/oauth/callback`.
4. Copy the **Application (client) ID** into the Microsoft Entra card of Settings > Integrations, or run:

```bash
wing integrations microsoft-client set --client-id 00000000-0000-0000-0000-000000000000
wing integrations connect onedrive --own-client
```

Each connected account gets a cloud volume addressed as `onedrive://<email>/` and a sidebar location `OneDrive (<email>)`, with index mode `none` like Google Drive. `OneDriveBackend` runs file operations through OpenDAL's OneDrive service, but refreshes tokens itself: OpenDAL's refresh always sends a client secret, which public clients must not send, and drops the refresh token Microsoft rotates on every refresh. `MicrosoftTokenSource` keeps the newest refresh token and writes it back to the library under a write lock, so the grant outlives the 90-day lifetime of the first token. OpenDAL gets only the current access token and is rebuilt when it changes. Deleting moves items to the OneDrive recycle bin. Capacity comes from Graph `/me/drive`.

Microsoft has no endpoint for an app to revoke its own grant. Disconnecting deletes the local secrets and unmounts OneDrive; the grant stays listed at [account.live.com/consent/Manage](https://account.live.com/consent/Manage) (or the tenant's My Apps page) until the user removes it.

## Where secrets live

Grants and custom clients are stored in the library's `cloud_credentials` table, encrypted with XChaCha20-Poly1305 under the library key, the same as cloud volume credentials. The email and profile are encrypted together with the tokens. Each library keeps its own accounts.

Access tokens stay in memory. `GoogleTokenSource` holds one per account, refreshes it two minutes before expiry under a lock, and shares it between the Drive volume and Photos jobs. A `401` drops the cached token and retries once. Rate limits (`429`, or `403` with a rate-limit reason) and `5xx` answers back off exponentially from 500 ms, up to four attempts.

Disconnecting an account removes its Drive location and volume, revokes the refresh token at Google, and deletes the stored secrets. If Google cannot be reached, the local copy is still deleted and the grant stays listed in the Google account's third-party access page.

## Google Drive volume

Each connected account with Drive gets a cloud volume addressed as `gdrive://<email>/`, plus a sidebar location named `Google Drive (<email>)`. The location uses index mode `none`, so connecting a large Drive does not start a crawl. Folders list live from the Drive API.

```text
gdrive://ana@example.com/Projects/report.pdf
```

`GoogleDriveBackend` implements `VolumeBackend` over Drive v3:

- **Paths over IDs.** Drive addresses files by ID and allows duplicate names in a folder. The backend lists each folder and gives every child a unique name. Duplicates become `name (2).ext` in creation order, so a path keeps pointing at the same file. A `/` in a name becomes `_`.
- **Google Docs.** Docs, Sheets, Slides and Drawings have no bytes of their own. They appear as `.docx`, `.xlsx`, `.pptx` and `.pdf` and download as exports. Writing to them is refused, and opening them goes to the browser. Forms, Sites and shortcuts are hidden.
- **Uploads** use Drive's resumable protocol in 8 MiB chunks, streamed from disk. After an interrupted chunk the upload resumes from the byte Google confirmed.
- **Downloads** read 8 MiB ranges into a `.wingpart` sibling and rename it into place, so a failed download leaves no truncated file.
- **Rename and move** inside Drive are a single server-side `PATCH`, folders included. **Copy** of a file is server side; folders are recreated file by file.
- **Trash.** Deleting to the trash moves the item to Drive's trash, where it can be restored. Permanent deletion is also available. Secure deletion is refused on cloud storage.
- **Revisions.** Listings carry `md5Checksum` (or the file version for Google Docs), which sync and cloud editing use to detect remote changes.
- **Capacity** comes from `about.storageQuota`.
- Listings are cached for 30 seconds and every write invalidates the folders it touches.

## Copying to and from the cloud

`FileCopyJob` hands a batch that involves a cloud volume to `ops::files::copy::cloud`, which moves bytes through `VolumeBackend`. Local to cloud, cloud to local and cloud to cloud all work, for files and folders. A copy between two cloud volumes goes through a temporary file. Conflicts follow the job's `FileConflictResolution` (overwrite, keep both, skip, abort). A move deletes each source only after its copy succeeded, and keeps a source folder that still holds skipped or failed items.

## Editing cloud files

Double-clicking a Drive file downloads it to `<data dir>/cloud-edit/<session>/` and opens that copy with the default app. The daemon checks the copy every 2 seconds and uploads it once a change has stayed the same for 2 seconds, so a save in progress is not uploaded half written. Polling a single file survives editors that save by renaming a temporary file over the original.

Before each upload WingDrive compares the cloud revision with the one it downloaded. If the file changed in the cloud meanwhile, the local edit is uploaded next to it as `name (conflict copy <date>).ext`, so neither edit is lost.

Settings > Integrations lists open sessions with their state. **Finish editing** uploads pending changes and deletes the local copy; if that upload fails, the copy is kept. Sessions older than 7 days are cleaned up when the daemon starts.

## Cloud sync

A sync pair keeps a local folder and a folder on a cloud volume in step. It works with any cloud volume, not only Google Drive.

| Mode | Behavior |
| --- | --- |
| `two_way` | Changes on either side reach the other |
| `upload` | The cloud folder mirrors the local folder |
| `download` | The local folder mirrors the cloud folder |

Each run lists both trees and compares them with the manifest saved by the last successful run. The manifest is what makes deletions safe: a file missing on one side counts as deleted only if both sides had it before.

- A first run never deletes anything. Files present on both sides with the same size are adopted without a transfer.
- Deletions propagate only with `propagate_deletes`, and only for files synced before. Local deletions go to the system trash; cloud deletions go to the service's trash when it has one.
- In `two_way`, when both sides changed a file, the local copy is renamed to `name (conflict copy <date>).ext`, the cloud version is downloaded, and the conflict copy is uploaded. An edit beats a deletion.
- Remote changes are detected by revision (MD5 or ETag) when the service reports one, otherwise by size and modification time.
- Partial downloads, `.DS_Store`, `Thumbs.db`, `desktop.ini` and Office or LibreOffice lock files are ignored. Local symlinks are skipped.
- A failing file is reported and left out of the manifest, so the next run retries it.

Pairs run on demand or every N minutes (5 or more). The scheduler checks for due pairs every minute, and a pair never runs twice at once. Two pairs cannot overlap on the same local or cloud folder.

```bash
wing integrations cloud-sync add Documents ~/Documents gdrive://ana@gmail.com/Backup/Documents --every 60
wing integrations cloud-sync run <id>
wing integrations cloud-sync update <id> --mode upload --propagate-deletes true
wing integrations cloud-sync list
```

## Google Photos

Since 2025-03-31 the Photos Library API only lets an app list and edit media and albums it created itself. Reading the rest of a library goes through the Photos Picker API, where the user selects items on a Google page.

- **Upload.** Photos and videos are streamed to `uploads` and turned into media items in batches of 50, optionally into a new or existing WingDrive album. Folders are walked and files Google Photos does not accept are skipped. The job is resumable without duplicates: it records every file whose media item exists.
- **Albums.** Lists the albums WingDrive created.
- **Import.** WingDrive creates a picker session and opens its page. Once the user presses Done, the import job downloads each item at original quality (`=d` for photos, `=dv` for videos) into the chosen folder, numbering names that already exist.

```bash
wing integrations photos upload <account-id> ~/Pictures/Trip --new-album "Trip"
wing integrations photos import <account-id> ~/Pictures/From-Google
```

## Testing

`core/tests/google_integration_test.rs` runs the whole flow against an in-memory fake of the Google APIs (`core/tests/helpers/fake_google.rs`): sign-in of two accounts through the real loopback listener, Drive listing with pagination and duplicate names, ranged downloads, Google Docs export, chunked resumable uploads, rename, copy, trash, a forced `401` recovered by a refresh, copy jobs in both directions, a volume refresh, cloud sync, Photos upload and picker import, a cloud editing session, and account removal with revocation.

`core/tests/microsoft_integration_test.rs` runs the Microsoft sign-in against a fake identity platform and Graph `/me`: the `app` mode, OneDrive mounted with its location and capacity, the rotated refresh token saved back, no client secret sent, the `custom` mode and account removal. OneDrive file operations go through OpenDAL to the real Graph and are not covered by the fake. `WINGDRIVE_MICROSOFT_ENDPOINTS_BASE` points sign-in and `/me` at another server.

`WINGDRIVE_GOOGLE_ENDPOINTS_BASE` points every Google API at another server, which is how a daemon can run against a fake for manual checks:

```bash
WINGDRIVE_GOOGLE_ENDPOINTS_BASE=http://127.0.0.1:18090 \
WINGDRIVE_GOOGLE_CLIENT_ID=test.apps.googleusercontent.com \
WINGDRIVE_GOOGLE_CLIENT_SECRET=test \
  ./target/debug/wing-server --data-dir /tmp/wing-check --instance check --port 18089 --auth disabled
```

<Warning>
	Never set `WINGDRIVE_GOOGLE_ENDPOINTS_BASE` on a daemon you use with real
	accounts. It sends authorization codes and tokens to that server.
</Warning>

## Status and roadmap

The integration is complete in code and tested against a fake of the Google APIs. On 2026-11-13 WingDrive's own Google client (project `wingdrive-514618`, published unverified) signed in to a real account from the Linux desktop app. Release builds read the clients from the repository secrets `WINGDRIVE_GOOGLE_CLIENT_ID`, `WINGDRIVE_GOOGLE_CLIENT_SECRET` and `WINGDRIVE_MICROSOFT_CLIENT_ID` (`release.yml`, `windows-bundle.yml`). The privacy policy is at https://wingdrive.org/privacy and the terms at https://wingdrive.org/service-terms. Remaining (epic `INTG-000`):

| Task | What |
| --- | --- |
| INTG-001 | WingDrive's Google Cloud project and OAuth client, bundled in release builds |
| INTG-002 | Privacy policy, terms and Limited Use disclosure on wingdrive.org |
| INTG-003 | Google OAuth verification; the restricted `drive` scope needs a yearly CASA assessment |
| INTG-004 | End-to-end validation with real Google on every platform |
| INTG-005 | Reconnect flow for revoked or expired accounts |

Until INTG-001 ships, Google sign-in needs the `custom` mode (see [OAuth client](#oauth-client)). OneDrive (INTG-022) still needs WingDrive's Microsoft app registration in release builds and a check against the real service. Other providers (Dropbox, Nextcloud, WebDAV, iCloud Drive, Box, pCloud, MEGA, Proton Drive, object storage, SFTP and SMB) are planned as INTG-021 to INTG-031 on top of a shared provider framework (INTG-020).

## Limitations

- Shared drives and "Shared with me" are not browsed; only "My Drive".
- Drive folders are listed live and not indexed, so Drive files do not appear in library search. Enabling indexing on the Drive location runs the generic cloud indexer, which has not been validated against Google Drive.
- Changes made in Drive appear on the next listing (cache of 30 seconds); there is no push notification channel.
- Google Docs, Sheets and Slides edit only in the browser.
- The Photos Library API cannot list photos WingDrive did not upload; use the picker to import them.
- OneDrive shows the signed-in user's own drive; SharePoint libraries and items shared with the user are not browsed.
