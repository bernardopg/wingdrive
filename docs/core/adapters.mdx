An adapter brings data from another app or service into a library as a source: notes, mail, code,
chat, browser history. It is a process. The daemon starts it, writes one JSON document on stdin,
and reads JSON lines from stdout. Python scripts and compiled programs speak the same contract.

Users install adapters from the store (Sources > Add source > Adapters, or `wing adapters install
<id>`). How the store publishes, signs and updates them is in
[`docs/design/adapter-store.md`](https://github.com/bernardopg/wingdrive/blob/main/docs/design/adapter-store.md).
This page is the contract an adapter follows. `ScriptAdapter` in `crates/archive/src/adapter/script.rs`
implements it.

## Folder

```
obsidian/
├── adapter.toml   manifest
├── sync.py        entry point (or a compiled binary)
├── icon.svg       square, under 64 KB, no scripts
├── README.md      ## Setup, ## Data, ## Privacy
├── fixtures/      test cases for `wing adapter test` (see Testing)
└── tests/
```

The store installs it under `<data dir>/adapters/installed/<id>/`. During development, point
`WINGDRIVE_DEV_ADAPTERS` at a folder of adapter folders and the daemon loads them too.

## Manifest

```toml
[adapter]
id = "obsidian"
name = "Obsidian"
summary = "Notes, tags and links from an Obsidian vault."   # store card, up to 140 characters
description = "Longer text for the details page."
version = "1.0.0"
author = "WingDrive"
license = "Apache-2.0"
icon = "icon.svg"
contract = 1
platforms = ["linux", "macos", "windows"]
categories = ["notes"]

[adapter.runtime]
kind = "python3"        # or "binary"
entry = "sync.py"
timeout = 300
detect = true          # answers "mode": "detect"

[adapter.permissions]
read = ["~/Documents"]  # paths it reads
network = []            # hosts it contacts
secrets = []            # config keys that hold secrets
tools = []              # programs it runs

[[adapter.config]]
key = "vault_path"
name = "Vault"
type = "string"
path_type = "folder"
required = true

[data_type]
id = "obsidian"
name = "Obsidian note"

[models.note]
fields.title = "string"
fields.body = "text"
fields.modified = "datetime"

[models.note.relations]
many_to_many = ["note"]

[search]
primary_model = "note"
title = "title"
preview = "body"
search_fields = ["title", "body"]
date_field = "modified"
```

`contract` is the version of this page the adapter speaks. The daemon refuses an adapter whose
contract is newer than its own. Folders without `contract` are contract 0 prototypes, which run
`runtime.command` through `sh -c`, inherit the daemon's environment and receive only the config on
stdin. Nothing in the store is contract 0.

Field types are `string`, `text`, `integer`, `float`, `boolean`, `datetime` and `json`. Each model
becomes a table keyed by `external_id`. `many_to_many` creates a junction table; a model related
to itself (`note` to `note`) gets one too.

## Process

| Runtime | Command |
|---|---|
| `python3` | `python3 -I <entry>` (`python` on Windows), so the adapter's folder is not on `sys.path` |
| `binary` | `<entry>`, built by the registry's CI from the reviewed commit |

The working directory is the adapter's folder. The environment is cleared down to `PATH`, `HOME`,
`LANG`, `LC_ALL`, `TZ`, `TMPDIR` and, on Windows, `SYSTEMROOT`, `USERPROFILE`, `APPDATA` and
`LOCALAPPDATA`. The daemon adds:

| Variable | Value |
|---|---|
| `WINGDRIVE_ADAPTER_ID` | `id` from the manifest |
| `WINGDRIVE_ADAPTER_VERSION` | `version` from the manifest |
| `WINGDRIVE_CONFIG_<KEY>` | each config field, upper case |

Prefer stdin over these variables.

## Isolation

On Linux every contract 1 adapter runs inside [bubblewrap](https://github.com/containers/bubblewrap)
(`bwrap`), with new mount, PID, IPC, UTS and user namespaces and no capabilities. Inside it the
adapter sees only:

| Path | Access |
|---|---|
| `/usr` and the system links into it, the dynamic loader cache, TLS certificates, DNS and time zone files under `/etc` | read |
| The adapter's own folder | read |
| Each path in `permissions.read` that exists, after `~` and `{config.<key>}` are expanded | read |
| `data_dir` | read and write |
| `/tmp` | an empty folder of its own |
| The network | only when `permissions.network` lists at least one host; otherwise none, not even the host's loopback |

The rest of the home folder, other users' files and the daemon's own data do not exist inside the
sandbox. Hosts in `network` are checked in review, not by the sandbox: an adapter that declares any
host can reach any host. `WINGDRIVE_ADAPTER_ISOLATION` tells the adapter how it runs
(`bubblewrap`, `flatpak` or `none`).

WingDrive checks once per start that bubblewrap works. When it is missing, or user namespaces are
blocked (Docker's default seccomp profile, some AppArmor setups), adapters do not run and the sync
explains why. Set `WINGDRIVE_ADAPTER_SANDBOX=off` to run them without confinement on purpose, for
example in a container that is itself the boundary.

| System | Confinement |
|---|---|
| Linux (AppImage, `.deb`, AUR, server archives) | bubblewrap, as above; the packages depend on it |
| Linux Flatpak | the Flatpak sandbox around WingDrive; adapters are not limited to their declared paths |
| Docker image | bubblewrap is installed; it needs user namespaces (`--security-opt seccomp=unconfined`) or `WINGDRIVE_ADAPTER_SANDBOX=off` |
| macOS and Windows | none yet: the permissions are what the registry reviewed |

The store shows which of these applies next to each adapter's permissions.

Test an adapter the way it will run: an access it did not declare fails inside the sandbox with
`FileNotFoundError` (the path does not exist there) or a network error.

## Input

stdin holds one JSON document, then closes:

```json
{
  "contract": 1,
  "config": { "vault_path": "/home/ana/Notes" },
  "cursor": "{\"v\":1,\"notes\":{}}",
  "data_dir": "/home/ana/.local/share/wingdrive/libraries/.../sources/4f2c/state"
}
```

| Field | Meaning |
|---|---|
| `config` | The fields the user filled when adding or editing the source, secret ones included |
| `cursor` | The last cursor the adapter printed for this source, or `null` on the first sync |
| `data_dir` | A folder for this source that only the adapter writes to (`<source folder>/state`); the source's database lives next to it, out of reach |

### Secrets

A config field with `secret = true` (an access token, a password) is never stored with the rest of
the source's settings. The daemon keeps it in the encrypted secret store of the WingDrive data
folder (`secrets.redb`, key `source-secret:<library>:<source>:<field>`), adds it to `config` only
for the run, and never returns it to the interface: editing a source shows the field as saved and
keeps the value unless a new one is typed. Sources created before 3.9 held secrets in the archive
registry; their next sync moves them to the secret store.

## Output

Each line on stdout is one JSON object. The daemon applies lines as it reads them.

| Line | Effect |
|---|---|
| `{"upsert": "note", "external_id": "a1", "fields": {...}}` | Insert or update a record; fields not in the model are ignored |
| `{"delete": "note", "external_id": "a1"}` | Delete a record and its links |
| `{"link": "note", "id": "a1", "to": "note", "to_id": "b2"}` | Add a `many_to_many` link; both records must exist |
| `{"unlink": "note", "id": "a1", "to": "note", "to_id": "b2"}` | Remove that link |
| `{"cursor": "..."}` | Store the cursor the next sync receives |
| `{"log": "info", "message": "..."}` | Log at `debug`, `info`, `warn` or `error` |

`external_id` is the adapter's own stable key for a record; derive it from something that survives
a restart, such as a relative path or a message id. For a `belongs_to` relation, put the parent's
`external_id` in the `<parent>_id` field; the parent must be upserted first.

Print the cursor last, after every record it covers. If the run dies before that line, the next
sync starts from the previous cursor and sends the same records again, which upserts make harmless.
A cursor is a string; JSON inside it is fine.

## Detect

An adapter that sets `runtime.detect = true` can suggest config values found on the machine, such
as the vaults Obsidian knows or the GitHub CLI's user. When the user opens the add source form,
the daemon runs it with:

```json
{ "contract": 1, "mode": "detect", "config": {}, "cursor": null, "data_dir": null }
```

and reads `{"suggest": {"<config key>": ["best value", "another"]}}` lines. The form fills each
field with its first suggestion and offers the rest. Detection has 15 seconds; a failure or a
timeout only means no suggestions. Never put secrets in a suggestion.

## Deletions

The daemon never compares what the adapter printed with what it stored, so an adapter that only
prints new and changed records must print deletions itself. Keep enough state in the cursor (or in
`data_dir`) to notice what disappeared since the last run.

## Errors

Exit with status 0 when the sync finished. Any other status marks the sync as failed, keeps what was
already applied, and shows the last line the adapter wrote to stderr as the error. Write diagnostics
to stderr or as `log` lines, never as plain text on stdout: the daemon skips stdout lines that are
not JSON and logs a warning for each.

## After the sync

New and changed records go through the source's safety screening, which decides whether they enter
the source's full-text index, and are embedded for semantic search.

## Testing

`wing adapter test <folder>` runs an adapter against its test cases the way the daemon runs it:
same stdin, same sandbox, the cursor of each run passed to the next. It needs no daemon. The
template CI and the registry's review checks run the same harness
(`wing_archive::harness::test_adapter`). The registry builds it as `wing-adapter-test`, a small
binary of the `wing-archive` crate that takes the same arguments, so it does not compile the whole
core:

```bash
cargo build --locked -p wing-archive --bin wing-adapter-test
target/debug/wing-adapter-test path/to/adapter [--case <name>]
```

Each case is a folder in `fixtures/`:

```
fixtures/
├── two-notes/
│   ├── config.json     the config a user would save; "{fixture}" is this folder's path
│   ├── expected.json   what the source must hold afterwards
│   └── folder/         any files the case points the adapter at
└── missing-folder/
    ├── config.json
    └── expected.json
```

```json
{
  "counts": {"note": 2},
  "records": [
    {"model": "note", "external_id": "groceries.txt", "fields": {"title": "groceries", "words": 4}}
  ],
  "absent": [{"model": "note", "external_id": "ignored.md"}]
}
```

| Key | Meaning |
|---|---|
| `runs` | How many times to sync. Default 2. |
| `idempotent` | Every run after the first keeps the record counts of the first. Default `true`; set `false` when the input changes between runs. |
| `error` | The first run must fail with an error that contains this text, as a missing folder should. |
| `counts` | Records per model after the last run. |
| `records` | Records that must exist, with the fields to compare. A value matches the text the database stores, so `4` matches `"4"`, and `null` matches a field the adapter left out. |
| `absent` | Records that must not exist. |

A case fails when a run fails without an `error` in `expected.json`, when the second run on the same
input adds or drops records, or when the stored records differ from `expected.json`. Each failure
is printed under its case, and the command exits with status 1. `--case <name>` runs one case.
`crates/archive/tests/fixtures/harness/notes` is a small adapter with two cases to start from.
