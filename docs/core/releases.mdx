WingDrive uses GitHub Actions workflows, git tags, and a custom xtask command to manage releases. This page covers the full release pipeline from version bump to published artifacts: Linux (AppImage, `.deb`, two AUR packages), Windows (NSIS `.exe` and `.msi`), Android and the server image.

## Versioning

WingDrive follows semver with pre-release suffixes for alpha/beta releases.

```
3.1.0-alpha.1   # Pre-release
3.1.0-beta.1    # Pre-release
3.1.0-rc.1      # Pre-release
3.1.0           # Stable release
```

Only `alpha`, `beta` and `rc` are accepted as pre-release labels (`scripts/release/version.py`).

The version string lives in 7 files across the repo:

- `core/Cargo.toml`
- `apps/server/Cargo.toml`
- `apps/cli/Cargo.toml`
- `apps/tauri/src-tauri/Cargo.toml`
- `apps/tauri/wing-tauri-core/Cargo.toml`
- `apps/tauri/src-tauri/tauri.conf.json`
- `apps/tauri/package.json`

These must stay in sync, together with `Cargo.lock`. The bump command handles this.

## Bump Command

`cargo xtask bump` updates all version files and `Cargo.lock`, then checks them with
`scripts/release/version.py`. It neither commits nor tags: `main` only changes through pull
requests, and the tag goes on the merge commit.

```bash
cargo xtask bump 3.1.0-beta.1
```

## Workflows

GitHub Actions workflows handle CI and releases.

### CI (`ci.yml`)

Runs on every pull request and push to `main`. Handles formatting checks, linting, and build verification. This is the standard PR gate.

### Desktop Release (`release.yml`)

WingDrive releases provide an x86_64 AppImage and a Debian package for Linux, and an NSIS `.exe`
and an `.msi` for Windows. `release.yml` first waits for every CI job on the tagged commit (the
`ci` gate), so a red Windows job also blocks a Linux release. The Windows installers come from
`windows-bundle.yml`, which installs each one, starts the daemon and the app, waits for the main
window and uninstalls it. Alpha, beta and rc tags ship the `.exe` only, because WiX accepts only
numeric pre-release versions. The installers are not signed yet (REL-001). The release
runner uses Ubuntu 24.04. The AUR package `wingdrive-bin` extracts the AppImage,
so launching the installed package does not require FUSE.

Run `scripts/setup.sh` to install native build dependencies, including
`patchelf` for the bundled GStreamer framework. Build the desktop with:

```bash
bun install --frozen-lockfile
bun run --cwd apps/tauri tauri:build --target x86_64-unknown-linux-gnu --bundles appimage,deb
```

Set the same version in the product manifests and lockfiles. Before creating a
version tag, run `python3 scripts/release/version.py v2.0.0-alpha.4`, replacing
the argument with your release version. Push the matching `v` tag to start
`.github/workflows/release.yml`.

The workflow checks types, native code, safe undo and secrets migration. It
builds both packages, starts the extracted AppImage with an isolated daemon,
opens 15 tabs and checks native PSS below 500 MiB, then runs the explorer browser tests against the production server. GitHub
publication starts after those checks pass. Prerelease versions retain their
alpha, beta or rc label.

The AUR job verifies the published checksums, builds the package with `makepkg`
in Arch Linux, runs the smoke test on the installed package, generates `.SRCINFO`, and pushes
changes using `AUR_SSH_PRIVATE_KEY` and `AUR_KNOWN_HOSTS`. Repeating the same publication leaves
unchanged AUR metadata untouched. Two packages carry the same AppImage and conflict with each
other:

| Tag | `wingdrive-bin` | `wingdrive-nightly` |
|---|---|---|
| `v3.1.0-alpha.1`, `-beta.N`, `-rc.N` | unchanged | updated |
| `v3.1.0` | updated | updated |

`wingdrive-nightly` therefore never trails `wingdrive-bin`. `scripts/release/aur.py` refuses a
pre-release for `wingdrive-bin`. To republish the AUR packages of an existing release, dispatch
`release.yml` with the tag and `aur_only`.

For a verification run, dispatch the workflow with an existing tag and leave
`publish` disabled. Desktop regression task TAURI-006 remains separate from
these release checks.

Opening an older `secrets.redb` upgrades its redb v2 file format. WingDrive
keeps a synced `secrets.redb.v2-<id>.backup` beside the database before the
upgrade. Keep that file until you have verified your libraries and secrets.

### Server Docker (`server.yml`)

Triggered by the same `v*` tag or manual dispatch. Builds a multi-arch Docker image (amd64 + arm64) and pushes it to GitHub Container Registry at `ghcr.io/bernardopg/wingdrive/server`.

The Docker build uses `buildah` with QEMU emulation for cross-platform images. The Dockerfile is at `apps/server/Dockerfile`.

**Tagging behavior:**

| Tag pushed | Docker tags applied | `latest` updated? |
|---|---|---|
| `v2.0.0-alpha.1` | `v2.0.0-alpha.1` | No |
| `v2.0.0-beta.1` | `v2.0.0-beta.1` | No |
| `v2.0.0` | `v2.0.0`, `latest` | Yes |
| Manual dispatch | `{short-sha}`, `staging` | No |

The `latest` tag only moves for stable releases (tags matching `vX.Y.Z` with no suffix). Pre-release tags like `alpha` or `beta` are published under their specific version only. This protects users pulling `latest` from getting unstable builds.

### Mobile (`mobile.yml`)

Runs on pull requests and pushes that touch the mobile app: lint, clippy for the embedded core on
`aarch64-linux-android`, and a Gradle release-variant build. `release.yml` calls it for every tag;
the `Signed Android release` job then builds the `.apk` (arm64-v8a) and the `.aab`, signed when the
four `WINGDRIVE_ANDROID_*` secrets exist, and hands them to the GitHub Release. Nothing is uploaded
to Google Play yet (MOB-009, REL-001). There is no iOS build in CI.

The app bundles `wing-mobile-core`, a native Expo module that wraps the WingDrive Rust core, so the
Android build needs the Cargo workspace and the Android NDK, not only JavaScript bundling.

## Release Flow

A full release looks like this:

```bash
# 1. Bump the version on a branch and add the CHANGELOG section
git switch -c release/v3.1.0
cargo xtask bump 3.1.0
just ci-local
gh pr create --title "chore(release): 3.1.0"

# 2. After the pull request merges and main's CI finishes, tag the merge commit
git switch main && git pull --ff-only
git tag -a v3.1.0 -m "WingDrive 3.1.0"
git push origin v3.1.0

# 3. Follow the run
gh run list --workflow release.yml --limit 1
```

Tag a commit whose CI already finished on `main`: `release.yml` then reuses that run instead of
starting a new one. Both `release.yml` and `server.yml` trigger from the same tag push.
`release.yml` publishes the GitHub Release after every verification passes, then the AUR packages.

## Discord

`discord.yml` posts to the WingDrive Discord server. Each push to `main` lists its commits in `#commits`. Each successful `release.yml` run posts that release's notes to `#changelog`, which is an announcement channel other servers can follow. Releases are created with `GITHUB_TOKEN`, which does not trigger `release` events in other workflows, so the post follows the release workflow's completion. Run the workflow by hand with a `tag` to post a release again.

Pull requests and issues reach `#github` through a repository webhook pointed at Discord's GitHub-compatible endpoint (`<webhook URL>/github`, events `pull_request` and `issues`). That endpoint cannot filter by branch, which is why the `main` and release feeds live in the workflow instead.

## Tauri Updater

Desktop updater endpoints and signing keys are not configured yet (REL-001). Install new versions through the AUR packages, the AppImage or Debian package, or the Windows installers from GitHub Releases. `wing update` checks for a newer release and prints the command or link for the way it was installed.

## Secrets

The release requires `AUR_SSH_PRIVATE_KEY` and `AUR_KNOWN_HOSTS` for AUR publication. Android signing uses `WINGDRIVE_ANDROID_KEYSTORE_BASE64`, `WINGDRIVE_ANDROID_KEYSTORE_PASSWORD`, `WINGDRIVE_ANDROID_KEY_ALIAS` and `WINGDRIVE_ANDROID_KEY_PASSWORD`; without them the bundle builds unsigned.

`discord.yml` reads `DISCORD_WEBHOOK_COMMITS` and `DISCORD_WEBHOOK_CHANGELOG`, the Discord webhook URLs of `#commits` and `#changelog`; without them it posts nothing and leaves a notice.

No workflow uses Apple, Authenticode, Tauri updater or Sentry secrets yet; REL-001 adds the signing
ones.

The Docker workflow uses only `GITHUB_TOKEN` which is provided automatically.
