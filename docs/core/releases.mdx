WingDrive uses GitHub Actions workflows, git tags, and a custom xtask command to manage releases. This page covers the full release pipeline from version bump to published artifacts.

## Versioning

WingDrive follows semver with pre-release suffixes for alpha/beta releases.

```
2.0.0-alpha.1   # Pre-release
2.0.0-beta.1    # Pre-release
2.0.0           # Stable release
```

The version string lives in 7 files across the repo:

- `core/Cargo.toml`
- `apps/server/Cargo.toml`
- `apps/cli/Cargo.toml`
- `apps/tauri/src-tauri/Cargo.toml`
- `apps/tauri/wing-tauri-core/Cargo.toml`
- `apps/tauri/src-tauri/tauri.conf.json`
- `apps/tauri/package.json`

These must stay in sync. The bump command handles this automatically.

## Bump Command

`cargo xtask bump` updates all version files, commits the changes, and creates a git tag.

```bash
cargo xtask bump 2.0.0-alpha.2
```

This does three things:

1. Updates the version string in all 7 files
2. Commits with message `v2.0.0-alpha.2`
3. Creates git tag `v2.0.0-alpha.2`

It does not push. You push manually when ready:

```bash
git push --tags
```

Pushing the tag triggers the release workflows.

## Workflows

GitHub Actions workflows handle CI and releases.

### CI (`ci.yml`)

Runs on every pull request and push to `main`. Handles formatting checks, linting, and build verification. This is the standard PR gate.

### Desktop Linux Release (`release.yml`)

WingDrive releases provide an x86_64 AppImage and a Debian package. The release
runner uses Ubuntu 24.04. The AUR package `wingdrive-bin` extracts the AppImage,
so launching the installed package does not require FUSE.

Run `scripts/setup.sh` to install native build dependencies, including
`patchelf` for the bundled GStreamer framework. Build the desktop with:

```bash
bun install --frozen-lockfile
bun run --cwd apps/tauri tauri:build --target x86_64-unknown-linux-gnu --bundles appimage,deb
```

Set the same version in the product manifests and lockfiles. Before creating a
version tag, run `python3 scripts/release/version.py v2.0.0-alpha.4`, replacing
the argument with your release version. Push the matching `v` tag to start
`.github/workflows/release.yml`.

The workflow checks types, native code, safe undo and secrets migration. It
builds both packages, starts the extracted AppImage with an isolated daemon,
opens 15 tabs and checks native PSS below 500 MiB, then runs the explorer browser tests against the production server. GitHub
publication starts after those checks pass. Prerelease versions retain their
alpha, beta or rc label.

The AUR job verifies the published checksums, builds the package with `makepkg`
in Arch Linux, generates `.SRCINFO`, and pushes changes using
`AUR_SSH_PRIVATE_KEY` and `AUR_KNOWN_HOSTS`. Both secrets must be configured in
the GitHub repository. Repeating the same publication leaves unchanged AUR
metadata untouched.

For a verification run, dispatch the workflow with an existing tag and leave
`publish` disabled. Desktop regression task TAURI-006 remains separate from
these release checks.

Opening an older `secrets.redb` upgrades its redb v2 file format. WingDrive
keeps a synced `secrets.redb.v2-<id>.backup` beside the database before the
upgrade. Keep that file until you have verified your libraries and secrets.

### Server Docker (`server.yml`)

Triggered by the same `v*` tag or manual dispatch. Builds a multi-arch Docker image (amd64 + arm64) and pushes it to GitHub Container Registry at `ghcr.io/bernardopg/wingdrive/server`.

The Docker build uses `buildah` with QEMU emulation for cross-platform images. The Dockerfile is at `apps/server/Dockerfile`.

**Tagging behavior:**

| Tag pushed | Docker tags applied | `latest` updated? |
|---|---|---|
| `v2.0.0-alpha.1` | `v2.0.0-alpha.1` | No |
| `v2.0.0-beta.1` | `v2.0.0-beta.1` | No |
| `v2.0.0` | `v2.0.0`, `latest` | Yes |
| Manual dispatch | `{short-sha}`, `staging` | No |

The `latest` tag only moves for stable releases (tags matching `vX.Y.Z` with no suffix). Pre-release tags like `alpha` or `beta` are published under their specific version only. This protects users pulling `latest` from getting unstable builds.

### Mobile Release (`mobile.yml`)

Manual dispatch only. Builds the React Native app for iOS and/or Android. A platform picker lets you build `ios`, `android`, or `all`.

The mobile app bundles `wing-mobile-core`, a native Expo module that wraps the WingDrive Rust core. This means mobile builds require the full Cargo workspace and Rust cross-compilation toolchain, not just JavaScript bundling.

**iOS (TestFlight):**

1. Compiles `wing-mobile-core` for `aarch64-apple-ios` via `cargo xtask build-mobile`
2. Runs `expo prebuild` to generate the Xcode project
3. Archives with `xcodebuild` using manual code signing
4. Exports IPA with `app-store-connect` distribution method
5. Uploads directly to TestFlight via `xcrun altool`

Runs on a self-hosted macOS ARM64 runner (same as desktop macOS builds). TestFlight handles distribution to testers automatically after upload.

**Android (Play Store Internal):**

1. Compiles `wing-mobile-core` for `aarch64-linux-android` via `cargo xtask build-mobile`
2. Runs `expo prebuild` to generate the Android project
3. Builds a signed AAB with `./gradlew bundleRelease`
4. Uploads to Play Store internal testing track

Runs on a Linux runner with Java 17 and the Android SDK/NDK.

<Note>The mobile workflow is manual dispatch only. It is not triggered by tags. Run it from the Actions tab when you want to push a mobile build to testers.</Note>

**Required secrets (in addition to existing Apple secrets):**

| Secret | Purpose |
|---|---|
| `MOBILE_PROVISIONING_PROFILE` | iOS App Store distribution profile for `com.wingdrive.app` (base64) |
| `ANDROID_KEYSTORE` | Android release keystore file (base64) |
| `ANDROID_KEYSTORE_PASSWORD` | Keystore password |
| `ANDROID_KEY_ALIAS` | Signing key alias |
| `ANDROID_KEY_PASSWORD` | Signing key password |
| `GOOGLE_PLAY_SERVICE_ACCOUNT` | Google Play API service account JSON (for automated upload) |

## Release Flow

A full release looks like this:

```bash
# 1. Bump version, commit, and tag
cargo xtask bump 2.0.0-alpha.2

# 2. Push the tag (triggers release + server docker workflows)
git push --tags

# 3. Wait for workflows to complete on GitHub Actions

# 4. Verify published GitHub assets and wingdrive-bin on AUR
```

Both `release.yml` and `server.yml` trigger from the same tag push. The Linux workflow publishes the GitHub release after verification, then updates AUR. Mobile releases use manual dispatch.

## Tauri Updater

Desktop updater endpoints and signing keys are not configured. Install new Linux versions through AUR or download the AppImage or Debian package from GitHub Releases.

## Secrets

The Linux release requires `AUR_SSH_PRIVATE_KEY` and `AUR_KNOWN_HOSTS` for AUR publication. Apple secrets apply to the experimental mobile workflow:

| Secret | Purpose |
|---|---|
| `APPLE_CERTIFICATE` | macOS code signing certificate (base64) |
| `APPLE_CERTIFICATE_PASSWORD` | Certificate password |
| `APPLE_SIGNING_IDENTITY` | Signing identity string |
| `APPLE_API_KEY` | App Store Connect API key ID |
| `APPLE_API_KEY_BASE64` | API key file (base64) |
| `APPLE_API_ISSUER` | API key issuer ID |
| `APPLE_PROVIDER_SHORT_NAME` | Team provider short name |
| `TAURI_PRIVATE_KEY` | Tauri update signing key |
| `TAURI_KEY_PASSWORD` | Tauri signing key password |
| `SENTRY_AUTH_TOKEN` | Sentry error tracking |

The Docker workflow uses only `GITHUB_TOKEN` which is provided automatically.
