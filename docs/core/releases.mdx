WingDrive uses GitHub Actions workflows, git tags, and a custom xtask command to manage releases. This page covers the full release pipeline from version bump to published artifacts, the asset list every release ships, the changelog standard and the layout of the release page.

## Release assets

Every stable release publishes exactly these files. `scripts/release/notes.py` refuses to publish a
release that lacks one of the required files, so the list on this page and the workflow cannot drift
apart. `<v>` is the version without the `v`.

| File | Platform | Built by | Required |
|---|---|---|---|
| `WingDrive-<v>-x86_64.AppImage` and `.sig` | Linux x86_64 | `release.yml` › desktop | yes |
| `WingDrive-<v>-amd64.deb` | Debian, Ubuntu | `release.yml` › desktop | yes |
| `WingDrive-<v>-x86_64.flatpak` | Any Linux with Flatpak | `flatpak-bundle.yml` | yes |
| `PKGBUILD`, `SRCINFO` | Arch Linux (`wingdrive-bin`) | `release.yml` › desktop | yes |
| `WingDrive-<v>-x64-setup.exe` and `.sig` | Windows x64 | `windows-bundle.yml` | yes |
| `WingDrive-<v>-x64.msi` | Windows x64 | `windows-bundle.yml` | stable only |
| `WingDrive-<v>-aarch64.dmg` | macOS Apple silicon | `macos-bundle.yml` | yes |
| `WingDrive-<v>-android-arm64-v8a.apk`, `WingDrive-<v>-android.aab` | Android | `mobile.yml` | when the keystore secrets exist |
| `wing-server-<v>-linux-x86_64.tar.gz`, `.tar.xz`, `.zip` | Linux x86_64 server and CLI | `release.yml` › server | yes |
| `wing-<v>-windows-x64.zip` | Windows CLI and daemon | `windows-bundle.yml` | yes |
| `SHA256SUMS` | All files above | `release.yml` › publish | yes |
| `latest.json` | Desktop updater | `release.yml` › publish | when the updater key exists |
| `LICENSE` | — | `release.yml` › desktop | yes |

The server image `ghcr.io/bernardopg/wingdrive/server:v<v>` (amd64 and arm64) comes from `server.yml`
on the same tag, and the AUR packages `wingdrive-bin` and `wingdrive-nightly` from the `aur` job after
publication.

Naming rules for new assets:

- Desktop and mobile packages start with `WingDrive-<v>-`, server and command line archives with
  `wing-server-<v>-` or `wing-<v>-`. Then the platform and architecture as the platform itself names
  them (`x86_64` on Linux and in AppImage, `amd64` in Debian, `x64` on Windows, `aarch64` on macOS).
- One extension per format. No spaces, no leading dot: GitHub drops a leading dot from asset names,
  which is why `.SRCINFO` ships as `SRCINFO`.
- Add the file to the table above, to `required_assets` and the download tables in
  `scripts/release/notes.py`, and to `website/src/views/Download.astro` in the same pull request.

Each build job writes `SHA256SUMS-<job>` next to its files. The publish job checks every one of them
after downloading the artifacts, deletes them, and writes a single `SHA256SUMS` for the release.

## Versioning

WingDrive follows semver with pre-release suffixes for alpha/beta releases.

```
3.1.0-alpha.1   # Pre-release
3.1.0-beta.1    # Pre-release
3.1.0-rc.1      # Pre-release
3.1.0           # Stable release
```

Only `alpha`, `beta` and `rc` are accepted as pre-release labels (`scripts/release/version.py`).

The version string lives in 7 files across the repo:

- `core/Cargo.toml`
- `apps/server/Cargo.toml`
- `apps/cli/Cargo.toml`
- `apps/tauri/src-tauri/Cargo.toml`
- `apps/tauri/wing-tauri-core/Cargo.toml`
- `apps/tauri/src-tauri/tauri.conf.json`
- `apps/tauri/package.json`

These must stay in sync, together with `Cargo.lock`. The bump command handles this.

## Changelog

`CHANGELOG.md` is the source of the release page and of the changelog on wingdrive.org, so it follows
one format, checked by `python3 scripts/release/changelog.py check` in the "Repository Metadata" CI
job. Sections from 3.7.0 on must follow it; older sections only need a valid heading.

```markdown
## Unreleased

## 3.7.0 — 2026-11-24

One paragraph for users: what this release is about, in plain words.

### Highlights

- The two or three changes a user should read first.

### Added

- One sentence per change, user-facing, past behavior named where it helps, then the pull
  request or task (#532, CORE-030).
```

- Heading: `## X.Y.Z — YYYY-MM-DD` with an em dash, the date the tag is pushed. Pre-releases use
  `X.Y.Z-alpha.N`, `-beta.N` or `-rc.N`. Newest first, no version twice.
- `## Unreleased` is optional and always on top. Pull requests that change behavior add their bullet
  there; the release pull request renames it to the version.
- A summary paragraph comes before the first subsection.
- Subsections, only these and in this order: `Highlights`, `Added`, `Changed`, `Fixed`,
  `Performance`, `Security`, `Deprecated`, `Removed`, `Internal`. Leave out the empty ones.
  `Internal` holds CI, tests, documentation and dependency work that users do not see.
- Every subsection holds `- ` bullets; continuation lines are indented two spaces. Write for users,
  name the platform when a change is platform-specific, and end with the pull request numbers.

`changelog.py require <version>` runs first in `release.yml`, so a tag without its section stops
before any build. `changelog.py extract <version>` prints one section.

## Release page

The publish job writes the release body with `scripts/release/notes.py` from the tagged
`CHANGELOG.md`, the verified files and the pull requests since the previous published release. The
title is `WingDrive <v>`. The body always has the same parts, in this order:

1. The version's `CHANGELOG.md` section. Versions tagged after the previous published release that
   never got a page of their own (3.6.0 and 3.6.1 for 3.7.0) follow under "Also in this release".
2. **Downloads**: tables for desktop and mobile, server and command line, and packaging and
   verification, with sizes, built from the files actually published. A file the tables do not know
   is listed under "Other files" rather than hidden.
3. **Verification**: how to check `SHA256SUMS`.
4. **Pull requests**: GitHub's generated list regrouped by Conventional Commits type (Features,
   Fixes, Performance, Security, Refactoring, Documentation, Tests, CI and build, Dependencies,
   Release, Maintenance), collapsed, with new contributors.
5. The compare link to the previous release.

Preview a body locally, without the GitHub API, from any directory holding the files:

```bash
python3 scripts/release/notes.py v3.7.0 <dist-dir> bernardopg/wingdrive /tmp/notes.md --offline
```

Pull request titles follow Conventional Commits (`feat(scope): …`, `fix: …`, `chore(deps): …`),
which is what puts them in the right group.

## Bump Command

`cargo xtask bump` updates all version files and `Cargo.lock`, then checks them with
`scripts/release/version.py`. It neither commits nor tags: `main` only changes through pull
requests, and the tag goes on the merge commit.

```bash
cargo xtask bump 3.1.0-beta.1
```

## Workflows

GitHub Actions workflows handle CI and releases.

### CI (`ci.yml`)

Runs on every pull request and push to `main`. Handles formatting checks, linting, and build verification. This is the standard PR gate.

### Desktop Release (`release.yml`)

`release.yml` runs these jobs on a `v*` tag, in parallel where they do not depend on each other:
`desktop` (AppImage, `.deb`, `PKGBUILD`, `SRCINFO`), `server` (server and CLI archives),
`flatpak` (after `desktop`), `macos`, `windows`, `android` and `ci`. `publish` needs all of them,
then `discord` and `aur` run. WingDrive releases provide an x86_64 AppImage and a Debian package for Linux, and an NSIS `.exe`
and an `.msi` for Windows. `release.yml` first waits for every CI job on the tagged commit (the
`ci` gate), so a red Windows job also blocks a Linux release. The Windows installers come from
`windows-bundle.yml`, which installs each one, starts the daemon and the app, waits for the main
window and uninstalls it. Alpha, beta and rc tags ship the `.exe` only, because WiX accepts only
numeric pre-release versions. The installers are Authenticode-signed only when the signing
secrets below exist (REL-001); without them the run warns and ships them unsigned. The release
runner uses Ubuntu 24.04. The AUR package `wingdrive-bin` extracts the AppImage,
so launching the installed package does not require FUSE.

Run `scripts/setup.sh` to install native build dependencies, including
`patchelf` for the bundled GStreamer framework. Build the desktop with:

```bash
bun install --frozen-lockfile
bun run --cwd apps/tauri tauri:build --target x86_64-unknown-linux-gnu --bundles appimage,deb
```

Set the same version in the product manifests and lockfiles. Before creating a
version tag, run `python3 scripts/release/version.py v2.0.0-alpha.4`, replacing
the argument with your release version. Push the matching `v` tag to start
`.github/workflows/release.yml`.

The workflow checks types, native code, safe undo and secrets migration. It
builds both packages, starts the extracted AppImage with an isolated daemon,
opens 15 tabs and checks native PSS below 500 MiB, then runs the explorer browser tests against the production server. GitHub
publication starts after those checks pass. Prerelease versions retain their
alpha, beta or rc label.

The AUR job verifies the published checksums, builds the package with `makepkg`
in Arch Linux, runs the smoke test on the installed package, generates `.SRCINFO`, and pushes
changes using `AUR_SSH_PRIVATE_KEY` and `AUR_KNOWN_HOSTS`. Repeating the same publication leaves
unchanged AUR metadata untouched. Two packages carry the same AppImage and conflict with each
other:

| Tag | `wingdrive-bin` | `wingdrive-nightly` |
|---|---|---|
| `v3.1.0-alpha.1`, `-beta.N`, `-rc.N` | unchanged | updated |
| `v3.1.0` | updated | updated |

`wingdrive-nightly` therefore never trails `wingdrive-bin`. `scripts/release/aur.py` refuses a
pre-release for `wingdrive-bin`. To republish the AUR packages of an existing release, dispatch
`release.yml` with the tag and `aur_only`.

For a verification run, dispatch the workflow with an existing tag and leave
`publish` disabled. Desktop regression task TAURI-006 remains separate from
these release checks.

Opening an older `secrets.redb` upgrades its redb v2 file format. WingDrive
keeps a synced `secrets.redb.v2-<id>.backup` beside the database before the
upgrade. Keep that file until you have verified your libraries and secrets.

### Flatpak (`flatpak-bundle.yml`)

`packaging/flatpak/com.wingdrive.desktop.yml` repackages the `.deb` of the same run on the GNOME 51
runtime, adds `libayatana-appindicator` from `flathub/shared-modules` (commit pinned in the workflow)
for the tray icon, and installs the binaries under `/app` with the Debian layout, so their RUNPATH
`$ORIGIN/../lib/wingdrive` still finds the media libraries. The job runs in the
`flatpak-github-actions:gnome-51` container, installs the bundle, checks that every library resolves
inside the sandbox and that the daemon answers `wing status`. Pull requests that change
`packaging/flatpak/` build it from the newest published `.deb`.

The app gets `--filesystem=host` and the removable media folders, because it is a file manager.
Volume detection inside the sandbox sees fewer mounts than a native install; the `.deb`, the
AppImage and the AUR packages remain the recommended Linux installs. Try a bundle locally:

```bash
flatpak install --user WingDrive-<v>-x86_64.flatpak
flatpak run com.wingdrive.desktop
```

### macOS (`macos-bundle.yml`)

Builds the Apple silicon app on `macos-15`, re-signs the bundled daemon with
`DaemonEntitlements.plist` (the app's sandbox entitlement would stop it), seals the app again ad hoc
and packs `WingDrive-<v>-aarch64.dmg` with `hdiutil`. The job mounts the image, verifies the
signature and the libraries, runs the daemon smoke test and starts the app until it spawns its
daemon. There is no Developer ID or notarization yet (REL-001, "Apple plan"): users clear the
quarantine once with `xattr -dr com.apple.quarantine /Applications/WingDrive.app`, and macOS is not
in `latest.json`, so the app does not update itself there.

### Server and command line archives

The `server` job packs `wing-server` and `wing` with `scripts/release/package_server.py`:
`bin/` with RUNPATH `$ORIGIN/../lib/wingdrive`, the FFmpeg and libheif libraries they load in
`lib/wingdrive/`, `LICENSE`, `NOTICE` and a `README.md`, as `.tar.gz`, `.tar.xz` and `.zip` with
fixed owners and timestamps. Each archive is extracted in an empty directory and started with an
empty environment until `/health` answers. `windows-bundle.yml` packs `wing.exe`, `wing-daemon.exe`
and their DLLs as `wing-<v>-windows-x64.zip` and runs both from the extracted folder with only
`System32` on `PATH`.

### Server Docker (`server.yml`)

Triggered by the same `v*` tag or manual dispatch. Builds a multi-arch Docker image (amd64 + arm64) and pushes it to GitHub Container Registry at `ghcr.io/bernardopg/wingdrive/server`.

The Docker build uses `buildah` with QEMU emulation for cross-platform images. The Dockerfile is at `apps/server/Dockerfile`.

**Tagging behavior:**

| Tag pushed | Docker tags applied | `latest` updated? |
|---|---|---|
| `v2.0.0-alpha.1` | `v2.0.0-alpha.1` | No |
| `v2.0.0-beta.1` | `v2.0.0-beta.1` | No |
| `v2.0.0` | `v2.0.0`, `latest` | Yes |
| Manual dispatch | `{short-sha}`, `staging` | No |

The `latest` tag only moves for stable releases (tags matching `vX.Y.Z` with no suffix). Pre-release tags like `alpha` or `beta` are published under their specific version only. This protects users pulling `latest` from getting unstable builds.

### Mobile (`mobile.yml`)

Runs on pull requests and pushes that touch the mobile app: lint, clippy for the embedded core on
`aarch64-linux-android`, and a Gradle release-variant build. `release.yml` calls it for every tag;
the `Signed Android release` job then builds the `.apk` (arm64-v8a) and the `.aab`, signed when the
four `WINGDRIVE_ANDROID_*` secrets exist, and hands them to the GitHub Release. Nothing is uploaded
to Google Play yet (MOB-009, REL-001). There is no iOS build in CI.

The app bundles `wing-mobile-core`, a native Expo module that wraps the WingDrive Rust core, so the
Android build needs the Cargo workspace and the Android NDK, not only JavaScript bundling.

## Release Flow

A full release looks like this:

```bash
# 1. Bump the version on a branch and turn "## Unreleased" into the version section
git switch -c release/v3.1.0
cargo xtask bump 3.1.0
python3 scripts/release/changelog.py check
just ci-local   # optional: every CI gate locally
gh pr create --title "chore(release): 3.1.0"

# 2. After the pull request merges and main's CI finishes, tag the merge commit
git switch main && git pull --ff-only
git tag -a v3.1.0 -m "WingDrive 3.1.0"
git push origin v3.1.0

# 3. Follow the run
gh run list --workflow release.yml --limit 1
```

Tag a commit whose CI already finished on `main`: `release.yml` then reuses that run instead of
starting a new one. Both `release.yml` and `server.yml` trigger from the same tag push.
`release.yml` publishes the GitHub Release after every verification passes, then the AUR packages.

## Discord

`discord.yml` posts to the WingDrive Discord server. Each push to `main` lists its commits in `#commits`. `release.yml` calls it once its publish job succeeds, and it posts that release's notes to `#changelog`, which is an announcement channel other servers can follow. The release is created with `GITHUB_TOKEN`, which fires no `release` event for other workflows, and only `release.yml` knows which tag it published. Verification runs and AUR-only reruns skip publish, so they post nothing, and an AUR failure after publish does not hold the post back. Run `discord.yml` by hand with a `tag` to post a release again.

The `#commits` feed relies on merges to `main` triggering push workflows. Auto-merge does so when `AUTO_MERGE_TOKEN` is set; its `GITHUB_TOKEN` fallback triggers no push workflows, so those merges skip CI on `main` and this feed alike.

Pull requests and issues reach `#github` through a repository webhook pointed at Discord's GitHub-compatible endpoint (`<webhook URL>/github`, events `pull_request` and `issues`). That endpoint cannot filter by branch, which is why the `main` and release feeds live in the workflow instead.

## Tauri Updater

The desktop app updates itself only where nothing else owns its files: the AppImage (the runtime sets `$APPIMAGE`) and the Windows installers. Copies installed by a package manager, the AUR packages `wingdrive-bin` and `wingdrive-nightly` and the `.deb`, report their package manager as the update channel and never download anything, so `pacman`, `yay` and `apt` stay the only writers of their files and their database keeps the real version. The AUR packages run the extracted AppImage from `/opt/wingdrive`, without `$APPIMAGE`, which is how the app tells them apart.

A stable tag builds the AppImage and the NSIS installer with `createUpdaterArtifacts`, signs them with the updater key and publishes their `.sig` files. The publish job then writes `latest.json` (`scripts/release/updater_manifest.py`) with the signed artifacts only. Installed apps read `https://github.com/bernardopg/wingdrive/releases/latest/download/latest.json`, which follows the newest stable release, and the updater plugin checks each signature against the public key in `apps/tauri/src-tauri/tauri.conf.json` before installing.

In the app, Settings > General > Updates shows the channel, checks on demand and installs with a restart. With "Check for updates automatically" on, the app checks once, 30 seconds after it starts, and shows a desktop notification when a release is waiting. `wing update` checks for a newer release and prints the command or link for the way it was installed.

### Updater key

The key pair was created on 2026-11-16 with `tauri signer generate`. The private key and its password are in the repository secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, and a copy of both, with the public key, is in the maintainer's Bitwarden vault, item "WingDrive Tauri updater signing key". Installed apps trust only this key: losing it means every user has to reinstall by hand to receive updates again, so never rotate it without a plan that ships the new public key first.

## Secrets

The release requires `AUR_SSH_PRIVATE_KEY` and `AUR_KNOWN_HOSTS` for AUR publication. Android signing uses `WINGDRIVE_ANDROID_KEYSTORE_BASE64`, `WINGDRIVE_ANDROID_KEYSTORE_PASSWORD`, `WINGDRIVE_ANDROID_KEY_ALIAS` and `WINGDRIVE_ANDROID_KEY_PASSWORD`; without them the bundle builds unsigned.

`release.yml` and `windows-bundle.yml` pass `WINGDRIVE_GOOGLE_CLIENT_ID`, `WINGDRIVE_GOOGLE_CLIENT_SECRET` and `WINGDRIVE_MICROSOFT_CLIENT_ID` to the builds, which compile them into `wing-core` as WingDrive's own OAuth clients (the "Google account" and "Microsoft account" sign-in in `docs/core/integrations.mdx`). Without them the build still works and users sign in with a client of their own.

`discord.yml` reads `DISCORD_WEBHOOK_COMMITS` and `DISCORD_WEBHOOK_CHANGELOG`, the Discord webhook URLs of `#commits` and `#changelog`; without them it posts nothing and leaves a notice.

`release.yml` and `windows-bundle.yml` read `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` to sign the updater artifacts; without them the bundles build unsigned and `latest.json` lists nothing.

`windows-bundle.yml` signs a tagged release with Authenticode through Azure Artifact Signing when six secrets exist: `AZURE_TENANT_ID`, `AZURE_CLIENT_ID` and `AZURE_CLIENT_SECRET` (the app registration that may sign), and `WINDOWS_SIGNING_ENDPOINT`, `WINDOWS_SIGNING_ACCOUNT` and `WINDOWS_SIGNING_PROFILE` (the account's regional endpoint, such as `https://wus2.codesigning.azure.net`, its name and the certificate profile). The run installs `artifact-signing-cli`, Tauri signs every program it bundles and both installers, and a step fails the run if an installer has no valid signature. A secret missing leaves a warning on the run and unsigned installers. Pull requests never sign.

No workflow uses Apple or Sentry secrets yet.

The Docker workflow uses only `GITHUB_TOKEN` which is provided automatically.
