## Overview

The WingDrive CLI (`wing`) is a command-line interface for interacting with the WingDrive daemon. It provides a comprehensive set of commands for managing libraries, files, devices, and daemon lifecycle.

## Architecture

The CLI follows a client-daemon architecture:

- **CLI Binary** (`wing`) - The client that sends commands
- **Daemon Binary** (`wing-daemon`) - The background service that does the actual work
- **Unix Socket** - Communication channel between CLI and daemon

```
┌─────────┐      Unix Socket      ┌──────────┐
│   sd    │ ◄──────────────────► │ wing-daemon│
│ (client)│                       │ (server) │
└─────────┘                       └──────────┘
                                       │
                                       ▼
                                  ┌──────────┐
                                  │ Libraries│
                                  └──────────┘
```

## Daemon Management

### Starting the Daemon

```bash
# Start in background
wing start

# Start in foreground (see logs)
wing start --foreground
```

The daemon:
- Runs as a background process
- Listens on a Unix socket at `~/Library/Application Support/wingdrive/daemon/daemon.sock`
- Manages all libraries and background tasks
- Can run multiple instances with `--instance` flag

### Auto-Start on Login

Install the daemon to start automatically on system boot:

```bash
# Install LaunchAgent (macOS)
wing daemon install

# Check status
wing daemon status

# Uninstall
wing daemon uninstall
```

This creates a LaunchAgent at `~/Library/LaunchAgents/com.wingdrive.daemon.plist` that:
- Starts daemon on user login
- Restarts if it crashes
- Logs to `~/Library/Application Support/wingdrive/logs/`

### Multi-Instance Support

Run multiple daemon instances for different data directories:

```bash
# Start with custom instance name
wing --instance work start
wing --instance personal start

# Each instance gets its own socket
# daemon-work.sock
# daemon-personal.sock
```

## Configuration

The CLI stores configuration in `~/Library/Application Support/wingdrive/cli.json`:

```json
{
  "current_library_id": "uuid-here",
  "update": {
    "repo": "bernardopg/wingdrive",
    "channel": "stable"
  }
}
```

### Config Commands

```bash
# View all configuration
wing config show

# Get specific value
wing config get update.repo

# Set value
wing config set update.repo "your-org/releases-repo"
```

## Checking for Updates

`wing update` checks the GitHub releases of `update.repo` (by default
`bernardopg/wingdrive`) and, when a newer release exists, prints how to install
it for the way this `wing` was installed. It never downloads or replaces
binaries: each published `wing` ships inside a package that owns its files.

| Installed through | `wing update` prints |
|---|---|
| AUR (`/opt/wingdrive`) | `yay -S wingdrive-bin`, or `wingdrive-nightly` for a pre-release |
| Debian package (`/usr`) | the `.deb` link and `sudo apt install ./<file>` |
| AppImage | the new AppImage's link |
| Windows installer | the new `.exe` or `.msi` link, matching the one installed |
| Source build (`target/`) | `git fetch --tags && git checkout <tag>` |

The `stable` channel, the default, only considers stable releases. The `beta` and
`nightly` channels also consider alpha, beta and rc releases, and so does an
installed pre-release:

```bash
wing update
wing config set update.channel nightly
```

## Command Structure

All CLI commands follow this pattern:

```bash
wing [--data-dir PATH] [--instance NAME] [--format FORMAT] <command> [args]
```

### Global Flags

- `--data-dir` - Override default data directory
- `--instance` - Connect to specific daemon instance
- `--format` - Output format: `human` (default) or `json`

### Core Commands

| Command | Description |
|---------|-------------|
| `wing start` | Start the daemon |
| `wing stop` | Stop the daemon |
| `wing restart` | Restart the daemon |
| `wing status` | Show system status |
| `wing update` | Update CLI and daemon |

### Domain Commands

| Command | Description |
|---------|-------------|
| `wing library` | Manage libraries |
| `wing location` | Manage indexed locations |
| `wing file` | File operations |
| `wing index` | Indexing operations |
| `wing search` | Search files |
| `wing tag` | Tag management |
| `wing volume` | Volume operations |
| `wing device` | Device management |
| `wing job` | Job control |
| `wing network` | Networking and pairing |
| `wing logs` | View daemon logs |
| `wing config` | Configuration management |
| `wing daemon` | Daemon lifecycle |

## Binary Distribution

For development and testing, binaries can be distributed without building from source:

1. **Build release binaries**:
   ```bash
   cargo build --release --bin wing --bin wing-daemon
   ```

2. **Copy both binaries** to target machine:
   - `wing` → keep as `wing`
   - `wing-daemon` → keep as `wing-daemon`

3. **Place in PATH**:
   ```bash
   mv wing ~/.local/bin/
   mv wing-daemon ~/.local/bin/
   chmod +x ~/.local/bin/wing ~/.local/bin/wing-daemon
   ```

4. **Remove quarantine** (macOS):
   ```bash
   xattr -d com.apple.quarantine ~/.local/bin/wing
   xattr -d com.apple.quarantine ~/.local/bin/wing-daemon
   ```

Both binaries must be in the same directory as the CLI expects to find the daemon binary in its parent directory.


### Adding New Commands

1. Create a new module in `domains/`
2. Define command enum with clap derives
3. Implement `run()` function
4. Register in `domains/mod.rs` and `main.rs`

Example:

```rust
// domains/myfeature/mod.rs
use anyhow::Result;
use clap::Subcommand;

#[derive(Subcommand, Debug)]
pub enum MyFeatureCmd {
    /// Do something
    Action { arg: String },
}

pub async fn run(ctx: &Context, cmd: MyFeatureCmd) -> Result<()> {
    match cmd {
        MyFeatureCmd::Action { arg } => {
            // Implementation
        }
    }
    Ok(())
}
```

## Security Considerations

### Instance Name Validation

Instance names are validated to prevent path traversal:
- Only alphanumeric, dash, and underscore allowed
- Max 64 characters
- Cannot be empty

### Binary Verification

The update system verifies downloaded binaries:
- File size must match release asset size
- Future: SHA256 checksum verification

### Daemon Socket Permissions

The Unix socket is created with restrictive permissions (user-only access).

## Troubleshooting

### Daemon Won't Start

```bash
# Check if already running
wing status

# View logs
wing logs follow

# Reset data and restart
wing restart --reset
```

### Update Fails

```bash
# Check configuration
wing config show

# Verify the releases are reachable
curl https://api.github.com/repos/bernardopg/wingdrive/releases
```

### Socket Connection Errors

The daemon socket is located at:
```
~/Library/Application Support/wingdrive/daemon/daemon.sock
```

If connection fails:
1. Verify daemon is running: `ps aux | grep wing-daemon`
2. Check socket exists: `ls -la <socket-path>`
3. Restart daemon: `wing restart`
