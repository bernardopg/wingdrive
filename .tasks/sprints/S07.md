## Proposed sequence for the first VDFS flow between two devices

Demonstrable result: on device B, search for a file indexed on A, see that the source is offline, reconnect A and get a verified copy. A second run must transfer zero bytes. Library sync replicates the catalog; moving the bytes needs an explicit user choice. Reference: [paper, Library Sync and Sync Conduits](../../whitepaper/upstream-whitepaper.tex).

| Order | Work | Acceptance criterion |
|---|---|---|
| 1 | CORE-023 and LSYNC-000. Validate incremental recovery with two daemons and separate databases. | B starts with no locations. While disconnected, A renames a file and both edit a tag. After reconnecting and restarting, both converge on the tag, B sees the new path, and ten idle minutes do not trigger another full backfill. |
| 2 | FILE-006 and FSYNC-003. Build a one-way copy preview from the indexes. | Show source, destination and byte count. An identical copy at another path is recognized by content. An offline volume shows as unavailable and the preview schedules no deletions. |
| 3 | FSYNC-003. Receive P2P transfers into a temporary file on the destination volume. | Dropping the connection and simulating a wrong hash keep the previous file. Publish the new name only after checking size and full hash. Also check the replacement on Windows. |
| 4 | FSYNC-004. Expose the search and fetch flow in the CLI. | With two independent profiles, search with A offline, reconnect, run the copy, verify the hash at the destination and repeat with no content traffic. Record commands, versions, bytes and result. |
| 5 | LSYNC-000. Evaluate a portable catalog after the minimal flow. | Moving a volume between two hosts keeps its identity and tags, updates the owner and keeps a single logical entry. Measure disk cost and recovery before choosing the stored format. |

### Evidence to reuse

- Verified receive, upstream `627680619`. The local path in core/src/service/network/protocol/file_transfer.rs still creates the destination directly. Adapt the temporary file lifecycle and the interruption cases to the current protocol.
- Incremental catch-up, upstream `ac4a53758`. WingDrive already documents the defect and drains in core/src/service/sync/peer.rs. Check the success and error paths in the step 1 scenario before importing changes.
- Portable identity, upstream `f69c1fee8`, and offline catalog, upstream `731744277`. Use them as reference for step 5. Upstream splits storage by source, and adopting it needs compatibility with existing libraries.
- In the review of main at 36e2e93e, sources and v2 were already fully contained in this history. The proposals above use individually identified commits. This analysis compares code and history; the acceptance criteria depend on runs in WingDrive.
